# 数据协议与信任边界

## 1. 事实范围

数据正文区分以下实体：

| 字段 | 含义 |
| --- | --- |
| `brands` | 消费者识别的品牌，不自动等于法律主体 |
| `entities` | 具体经营主体 |
| `sites` | 归属具体主体的办公室、工厂、门店、仓储或其他地点 |
| `brandSites` | 品牌与地点的多对多关联，说明自有、运营或合作供应商及产品范围 |
| `observations` | 该地点、岗位、用工类型和期间的作息资料 |
| `evidence` | 公开资料类型、短摘要、原文链接、发布日和复核日 |
| `shoppingLinks` | 主流购物平台的商品、店铺或搜索链接，三者明确区分 |
| `stores` | 公开零售门店位置，与生产厂区地址区分 |

“上游办公室、下游工厂”作为用户可理解的业务层次，不当作固定法律或供应链归属关系。办公室与工厂可能属于不同法人；一个代工厂也可以服务多个品牌。列出关系本身需要证据，不能仅凭名称关联。

UI 汇总不评定整个品牌“好 / 坏”。发现多个安排时展示“地点 / 岗位有差异”；来源不足、资料过期、岗位不明分别保留。没有资料不能显示“不双休”。180 天后的观察资料提示重新核实，这只是产品复核周期，不是法律标准。

## 2. 签名格式

单个 UTF-8 JSON 文件，推荐扩展名 `.sxlist.json`，上限 2 MiB。最后一个字段是公开签名串，并非秘密 key：

```json
{
  "format": "rest-evidence/v1",
  "keyId": "maintainer-2026",
  "body": {
    "schemaVersion": 1,
    "datasetId": "mainland-weekend",
    "environment": "production",
    "sequence": 1,
    "publishedAt": "2026-09-18T12:00:00+08:00",
    "expiresAt": "2026-10-18T12:00:00+08:00",
    "brands": [],
    "entities": [],
    "sites": [],
    "brandSites": [],
    "observations": [],
    "evidence": [],
    "shoppingLinks": [],
    "stores": []
  },
  "signature": "BASE64_ED25519_SIGNATURE"
}
```

此为格式示意，不是可导入的有效签名文件。

签名输入：

```text
UTF8("rest-evidence:dataset:v1\n" + JCS({format, keyId, body}))
```

使用 `canonicalize` 实现 JSON Canonicalization Scheme；签名算法 Ed25519，签名值 Base64 编码。SHA-256 用于对相同签名输入生成摘要、同版本内容冲突检查和展示。代码不自行实现密码学算法。

签名针对 JSON 的语义正文；缩进、对象字段顺序等格式变化不改变签名。字段值、日期、版本、关联关系、证据和链接都在签名范围内。

## 3. 为什么不把秘密 key 写进 App

盐值不是私钥。普通 SHA-256 允许修改者重新计算；HMAC 或“正文 + 日期 + 秘密 key”的方案若在客户端内置秘密，会随开源代码或二进制分发。取得该秘密的人就能伪造名单。

现在只有维护者持有 Ed25519 私钥，App 仅持有公开验签密钥。公钥无需保密；可信公钥列表必须经可信的 App 更新发布，不能由待导入名单自我声明。

密钥附带 `purpose` 和有效期。演示密钥只能验证 `environment=demo`，无法升级成正式数据。当前是单维护者签名，暂不实现多方门限签名或独立透明日志。

## 4. 导入、更新与缓存

```text
本地文件 / GitHub 原始文件
    -> 大小和格式检查
    -> 内置公钥选择
    -> Ed25519 验证
    -> Schema 和关联完整性检查
    -> 用途、密钥时间与未来时间检查
    -> 本机版本高水位检查
    -> 原子替换本地数据
    -> 根据名单与逐条观察时间显示时效
```

GitHub 更新只访问配置仓库的固定名单路径，不带 Token 或 Cookie。超时、HTTP 错误、文件超限、签名失败均不更新现有数据。更换 GitHub 仓库不能绕过公钥验证。

缓存使用同一条 localStorage 记录保存正文、版本高水位和最近 20 次更新。启动时重新验签；写入失败不切换页面数据。清除当前名单保留高水位；清除浏览器站点数据会同时移除高水位，这个边界无法靠纯客户端保证。

过期但签名有效的名单可用于历史查阅，始终提示过期。离线状态无法证明“这就是最新版本”，也无法获知刚发生的撤回或密钥泄露。第一次导入旧签名名单且没有本机历史时，只能根据有效期与用户所取得的可信版本判断。

## 5. 日期能证明什么

- `publishedAt` 是维护者写入并签名的签发日期，能发现第三方修改日期。
- 它不是可信时间戳服务出具的时间，不能独立证明真实签发时刻，不能阻止持钥者回填日期。
- `expiresAt` 是名单整体复核期限，不延长里面每条事实的观察期限。
- `periodStart` / `periodEnd` 是资料所覆盖的观察范围；`reviewedAt` 只是复核来源的日期。
- 设备时钟可能不准；客户端只能拒绝明显的未来日期，并提示用户检查时钟。

如后续确需强时间证明，可引入独立时间戳或透明日志，不能把 SHA-256 当作可信时钟。

## 6. 投稿与发布不是同一步

```text
填写具体主体、地点、岗位、期间、作息、公开来源
    -> 公开投稿提示与初步信息检查
    -> 用户在 GitHub 确认提交 Issue
    -> 维护者核验、处置争议、必要时暂不收录
    -> 审核后的 dataset.json
    -> 维护者签名
    -> 发布 latest.sxlist.json
```

Issue 和 PR 不能直接触发可信签名。CI 不得对来自未受信任 PR 的代码提供签名私钥；尤其不能在持有秘密的 `pull_request_target` 环境执行投稿者代码。当前签发采用本地命令，由维护者手动运行。

公开 GitHub 投稿无法实现“先私密审核，再公开原始 Issue”。App 只控制自己的投稿表单和签名名单，不能阻止别人绕过表单直接发 Issue。仓库仍需人工管理、快速移除泄露内容；真正私密举证需要另建合规受理渠道。

## 7. 软件本身的信任

列表验签以 App 和内置公钥本身可信为前提。攻击者若能够替换 App 的 JavaScript、公钥和 UI，同源网页上的验签标志也可以被伪造。生产发布需要保护代码仓库、发布账号、依赖和构建过程，公开版本摘要并采用适合平台的应用签名机制。

私钥泄露后需停止签发、更换密钥、发布可信 App 更新并通知用户。尚未更新或长期离线的客户端仍可能信任旧密钥，不能承诺远程彻底撤销已下载文件。

GitHub 访问能力按网络实际情况判断，不检测、安装或提供 VPN。无法访问时提供离线文件路线。
